# 第一部分｜评审报告（构建者记录）

## A. 结论

**holds up with caveats** —— **导播/机位层是真实可用的**，它完成了这个 Demo 的技术职责；但「360° 当作旋转」这一主张、以及三种 16:9 比例模式，**没有被画面兑现**。

## B. 主要发现

**B1｜RING 的「旋转」在世界空间里是空操作（no-op）。**
着色器用**未旋转**的世界方位角计算覆盖弧（`float az = atan(vPos.x, vPos.z)`；只有全景采样用了 `a = az - uRotate`）。用 `?pano=front-window` 隔离出那段弧，把 TOP 视角在 t=8 / 16 / 23 与默认全景对比：
- 弧像素数 **71680 / 71855 / 71903**
- 质心 **(331,682) / (330,682) / (330,682)**
- 30° 分箱角度直方图三次**完全相同** `[0,29926,33943,0,0,0,0,2220,4708,0,883,0]`

而同一区间 HUD 的「旋转」读数是 55° → 135° → 163°。**一个本该改变"内容在哪里"的状态变量，什么也没改变。**

**B2｜四种比例模式里有三种是同一张画。**
PERFORMER_FRONT、t=20 PEAK、1600×900 平均绝对差：pano↔repeat **1.90**、pano↔fill **3.01**、repeat↔fill **2.38**，而 pano↔front-window **15.27**。TOP 视角下 pano↔repeat = 0.01、pano↔fill = 0.01、repeat↔fill = 0.00（差异像素 0.00–0.02%）。点亮面积 48.99 / 48.56 / 48.61% vs front-window 19.87%。
原因：`repeat` 与 `fill` 采样的是同一条 `TILE_U0=0.39, TILE_W=0.22` 切片，且该切片本身几乎没有可辨识特征。**这直接否证了 status.json 里「三种处理直接暴露比例会怎样崩」的说法。**

**B3｜front-window 相对它服务的机位是偏心的。**
`win` 以世界 +Z 为中心，而 `srcU` 把切片的**右上角**映射到正面中心。它给的证据是 TOP 视角截图里亮弧落在环的**右侧**而非正面。

**B4｜blow-through 读得出来，内容读不出来。**
8 根加色灯柱（RGB 250.8, 220.8, 166.2）与 halo 在每个画面里都占主导，而屏幕内容是一片近乎均匀的噪点场；源里唯一的方位线索（4 个 8px 宽的象限标记）在所有渲染里都不可见。**PERFORMER_FRONT 里那条"地平线带"其实是穿过屏幕平面的灯柱，不是屏幕内容。**
另外：`scene.json` 声明了 `structure.scaleBarM: 5`，但 **main.js 从未绘制它**（sphere 是画了的）。

**B5｜performer 无法承担尺度。**
BOWL_WIDE t=20 在 performer 附近（≈790,495）实测 max RGB (126,112,131)、框均值 (43,44,48) —— **完全分离不出人形**。PERFORMER_FRONT 里身体为 (74.5,64,54)，灯柱为 (250.8,220.8,166.2)，只是一个暗剪影。blow-through 被证明了（人确实透过前壁可见），但 1.7 m 的人承担不了尺度，也无法在切换机位时作比较。

## C. 导播（这是本 Demo 的主题）——真实可用

切机位是**真的**：帧号与按下的按钮在文档化的时刻发生变化（t=2/6 LOW→BOWL_WIDE、t=10 BUILD→PERFORMER_FRONT、t=18 PEAK→ORBIT_45、t=26 RELEASE→TOP、t=30 RELEASE→BOWL_WIDE）。

**切换改变的是"读法"而不只是缩放：** BOWL_WIDE 里看不出 performer；PERFORMER_FRONT 在 t=10 同时揭示了 performer 与"屏幕是透明的"；ORBIT_45 给出另一组灯柱与从环内侧看的视角；TOP 是唯一能读出 **20m 圆柱 / 12m 人物区 / 30m 舞台同心关系**的机位。

**Program Out 可区分：** 全幅 program 画面 + 用 scissor 渲染的四分屏，program 图块有 `#7cc4ff` 描边、对应 HUD 按钮处于按下态。caveat：那 1px 描边是唯一的画面内标记；右下角 `.cut` 提示（y≈862）在 1578×802 录屏里与 TOP 图块区域重叠；四分屏是在 program 之后渲染的，所以图块叠在 program 之上。

## D. 状态区分

- **LOW**（t=4）：覆盖 91°/旋转 0°，只有环的亮半边有内容，正面近乎全黑。
- **BUILD**（t=12）：覆盖 180°，半环点亮——视觉上就是 LOW 移了一条切片边界。
- **PEAK**（t=20）：覆盖 360°，整环点亮，源最密最亮。
- **RELEASE**（t=28）：覆盖 80°/旋转 172°，弧塌回正面窗口——**BOWL_WIDE 的 t=4 与 t=28 几乎是同一帧**。

**直说：区分不是真的。** 唯一的状态变量是覆盖弧角度（外加弧内密度/亮度）；没有任何物体、位置或关系在状态之间改变，而"旋转"分量完全不产生可见变化。

## F. 未被支持 / 过度宣称

1. **HUD「旋转 N°」** —— 无法支持（见 B1）。
2. **HUD「展开比 7.85:1」** —— 无论哪个模式都照打；repeat 模式下实际画出的 tile 约 **1.96:1**。
3. **`scene.json` 注记「16:9 源只占正面 ±45°」** —— 判决认为着色器只照亮 ±0.12 rad ≈ ±7°（**构建者按：这条是评审误读，0.12 是羽化宽度，亮窗实际是 ±45°；但下面的 B3 观察仍值得复核**）。
4. **「95,000」在页面上根本没有出现**（main.js / index.html 均无匹配），只用 r=60m 的一圈 96 个刻度表示，而这圈刻度在除 BOWL_WIDE 外的所有机位都在画外。
5. **8m 高度确实被正确标注为教学 proxy**（角标 + scene 注记），**但 0.4 的高径比渲染结果与参考截图矛盾**——参考照片里圆柱"大致和它一样宽地高"，"rises like a beacon"在 8m/20m 下复现不出来，而 Demo 从未标注这一张力。
6. **`structure.scaleBarM: 5`** —— 声明了但从未绘制。

# 第二部分｜构建者裁定（LEAD / BUILD）

## 1｜结论：接受（两条修正）

**接受「holds up with caveats」以及 D 段「区分不是真的」。** 这一轮它指出了**一个真正的空操作 bug**——这是三轮评审里最容易被漏掉、也最有价值的一类问题：**我用一个状态变量驱动了一个不会移动的几何**。

两处我修正它的读法：

- **F3 关于 ±7°：** `smoothstep(PI*0.25-0.12, PI*0.25, azAbs)` 里 0.12 是**羽化宽度**，不是亮窗半宽；亮窗是 |az| ≤ 45°（π/4），只有边缘 7° 在渐变。它把羽化当成了窗口。
- **B3 的 off-centre：** `suv.u = (az/(π/2) + 0.5) * TILE_W` 在 az=0 处取的是切片**中点**，即亮窗确实以世界 +Z 为中心，逻辑上不偏心；它在 TOP 视角看到"弧在右侧"很可能来自 TOP 机位（相机在 (0,62,0.5) 近垂直俯视）的**方位约定**——这本身是可读性问题，V2 要在 TOP 视角加方位标记，而不是改映射。

除此之外**全部成立**，包括它自己承认的"导播层是真的"。

## 2｜已确认的根因

| # | 根因 | 性质 |
|---|---|---|
| B1 | `cover` 用未旋转的 az 计算，只有采样用了 `a = az - uRotate` | **状态变量空操作**——我的着色器接线错误 |
| B2 | repeat / fill 采样的切片（u∈[0.39,0.61]）本身无特征，四种模式里有三种在画面上等价 | 我的素材设计错误 |
| B4/F6 | 声明了 `scaleBarM` 却从未绘制 | 声明与实现脱节（与 Sphere 当初的发现同类） |
| B5 | performer 在广角机位完全不可分离 | 摆放与亮度问题 |
| F4 | 「95,000」只在一个多数机位看不见的刻度圈里 | 表达错误 |
| F5 | 8m 高度作为 proxy 与参考照片的高径比矛盾，且未标注张力 | proxy 选择不当 |
| D | 四状态只是同一个场景换弧角 | 状态设计不足 |

## 3｜V2 范围

brief 对这个 Demo 的要求是「改 camera sequence + 至少一个视觉状态」。V2 会超过这个下限：

| 轴 | V2 要做 |
|---|---|
| **状态节奏** | 修 B1：`uRotate` 必须同时作用于**覆盖弧**，让"旋转"真的把内容移到别处；四状态要改变**关系**而不只是角度——例如 PEAK 让灯柱从屏后穿到屏前、RELEASE 让 95,000 的环刻度亮起回到"被环绕" |
| **构图面积** | 修 B2：把切片素材换成**高对比、强非对称**的图形，使「1 条拉伸 / 4 条重复 / 前区窗口」在画面上一眼可分；HUD 的「展开比」改为按模式显示**实际**比值；补上声明过的 5m 比例尺 |
| **观看关系** | 修 B5：让 performer 在广角机位也能读（提高对比/尺寸参照），并在 TOP 视角加方位标记（回应 B3 的可读性）；把 95,000 的规模表达改成**在画面内可读**的形式 |
| **proxy 诚实** | 检讨 8m 高度：参考照片显示圆柱高径比接近 1:1，8m 是过矮的 proxy。V2 要么把高度调到更接近照片（并在角标说明这是**依据照片比例的选择**而非参考公布的数字），要么保留 8m 但**明确标注"与参考照片比例不符"** |

## 4｜三轮评审的类型差异（值得记录）

- Sphere：找到了**单位混淆**类错误，我否证了一条。
- Festival：找到了**空间安排**错误（缺口比地标还宽、人站错位置），全部成立。
- Installation：找到了**方法论**错误（这个 Demo 没有在测它声称要测的东西）。
- Stadium：找到了**空操作**错误（变量驱动了不会动的东西）+ **素材无法承载对照**（四种模式的素材无特征）。

四类问题都不重样，而且都是**看画面看不出来**的——这本身就是"为什么要预演、而且要独立评审"的最好论据。
